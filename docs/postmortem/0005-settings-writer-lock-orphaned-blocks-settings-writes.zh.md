# 事故复盘 0005：孤立的设置写入锁静默阻断了所有设置写入

[English](0005-settings-writer-lock-orphaned-blocks-settings-writes.md) | 中文

状态：已解决

## 执行摘要

一次在设置写入过程中发生的服务器异常重启，把已死进程的 `settings.yaml.lock` 留在了磁盘上。`withFileLock` 从不移除已存在的锁，因为文件年龄无法证明其持有者已停止——孤儿锁的清理在设计上刻意属于操作员动作——因此此后的每一次设置写入都会等满两秒的时限，并以 `settings/rejected: atomic-write: timed out waiting for the writer lock` 失败。浏览器侧的设置 scope 会把写入被拒当作可恢复情形：它重载镜像并正常返回，于是这些失败完全不可见：导航排序和主题切换都只是毫无反应。用户报告的「排序有时失效」因而主要来自被阻断的写入路径，而非拖拽代码；拖拽 drop 在快速拖拽时确实还有一个读取过期悬停状态的次要竞态，已单独修复。删除孤儿锁及其残留的临时文件后，写入立刻恢复。本记录不附带任何代码改动：孤儿锁自动恢复仍按设计搁置，因为在 Windows 上被复用的 PID 可能误清一个仍在写入的写者的锁，而 `dsh-atomic-write` 同时守护着凭据写入路径。

## 概述

[`withFileLock`](../../packages/util/atomic-write/src/index.ts) 通过一个 `wx` 排他创建的 `<file>.lock` 兄弟文件（内容为持有者的 PID）来串行化同一文件的写入者，并在 `finally` 中删除该文件。写入者在创建锁与执行 `finally` 之间被杀，就会留下一把没有持有者的锁。该协议刻意把这种孤儿锁交给操作员清理：竞争者只会退避重试，并在默认两秒后失败，而不会去猜测 PID 是否已过期——因为文件年龄无法证明持有者已停止，且被复用的 PID 可能清掉仍在写入的写者的锁、导致并发写损坏数据。

[settings-file 提供方](../../packages/settings/settings-file/src/index.ts) 的每个命名空间提交都经过这把锁（读-改-写：从磁盘对账、渲染、原子改名）。孤儿锁存在期间，每一次 `settings/mutate` RPC 都会以锁超时被拒。客户端 [`SettingsScope`](../../packages/client/ui-settings/src/client/settings-scope.ts) 把被拒的写入当作可恢复：它重载镜像并正常返回，于是 UI 保持写入前的顺序，没有任何错误提示。用户的体感就是一个静默不生效的功能。

## 影响

在受影响实例上，从 23:38 重启起到操作员删除锁为止，所有设置写入都处于失效状态：导航排序、主题偏好以及任何其他偏好写入。失败对用户不可见，设置 scope 层也不产生任何诊断——只有线上传输的 Host 侧 `settings/rejected`。没有任何数据损坏：原子改名提交从未执行，磁盘上的文档始终停留在最后一次提交的状态。

## 时间线

- 23:37–23:38 发生了一次设置备份与服务器重启（`settings.yaml.bak-fix-volc-context-20260908-235600`，随后新 web 服务器 PID 20440 于 23:38:48 启动）。
- 将死的进程留下了 `settings.yaml.lock`（内容为 PID 70852，现已死亡，创建于 23:38:28）以及 23:38:46 的在途临时文件 `settings.yaml.dbcfd7130fa1.tmp`。
- 此后的每次设置写入都以 `settings/rejected: atomic-write: timed out waiting for the writer lock at ...\settings.yaml.lock` 失败；客户端重载镜像并显示无变化。
- 诊断通过直接探测 `settings/mutate` 定位到写入路径，并确认锁的所有者 PID 已死；删除锁与过期临时文件后，主题与排序写入立刻恢复。

## 根因

锁协议按设计没有孤儿锁恢复，而客户端让「被拒的写入」与「无操作」无法区分。两者叠加，把一个可用性问题变成了静默的功能失效：写入路径宕了，却没有任何信号。拖拽交互还贡献了一个独立的偶发原因——快速拖拽时 drop 读取了 React 尚未提交的悬停状态——在写入路径未参与的情况下也会产生同样的症状。

## 已添加的防护

- 本记录不附带任何代码改动（操作员决定保持现状）。操作员恢复步骤为：确认锁内容的 PID 已死，删除 `settings.yaml.lock` 及任何残留的 `settings.yaml.<后缀>.tmp`，然后重试写入。
- 拖拽 drop 竞态已修复：drop 从 drop 事件本身解析目标行与半区，未派发 drop 的 `dragend` 回退到最后一次悬停的位置，并以每次拖拽一个标志防止重复提交。
- 按设计搁置：读取锁内 PID、探测存活并在已死时删除重试的孤儿锁自动恢复——因被复用的 PID 可能误清仍在写入的写者的锁而未实现，且 `dsh-atomic-write` 同时守护凭据写入路径。

## 教训

- 一条吞掉拒绝的写入路径，会把可用性 bug 变成「功能坏了」的报告。一次直接的 `settings/mutate` RPC 探测就能区分 UI 竞态与持久化失败，是设置写入「有时失效」时应当做的第一步。
- 进程异常死亡后出现孤儿锁是常态；排查设置写入的人应首先知道操作员动作（验证 PID、删除锁与过期临时文件），再动提供方。
- 文档化的设计决策（不清自动锁）只有在存在且众所周知的操作员动作时才安全；残留代价是可诊断性，这里用书面恢复步骤来缓解。
